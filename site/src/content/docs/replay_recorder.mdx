All settings for this feature live under <ToolboxPath steps={["Settings", "Replay Recorder"]} />. The module is off by default: turn it on under <ToolboxPath steps={["Settings", "Toolbox Modules"]} />.

The Replay Recorder saves every message the game server sends while you are in a PvE map, from entering the map until leaving it, with the time each one arrived. It only reads what the client already received and changes nothing in the game. PvP maps and observed matches are never recorded. A recording can be played back in the game's own observer mode, from the Observe window (see [Playing a recording](#playing-a-recording)).

A recording starts when you enter a map, so enable the module before you travel or zone. Leaving the map, logging out or a minute without any message from the server ends it.

## Settings

- **Record explorable areas** — record explorable areas and missions (on by default).
- **Record outposts** — also record outposts and towns.
- **Keep other players' names and chat out of recordings** — on by default. Other players' names become `Player 1`, `Player 2`... (the same player keeps the same label within a recording) and player chat and player speech bubbles are left out. Every name the server sends as plain text is relabelled this way; NPC chat and system messages are kept.
- **Keep my own names out of recordings** — on by default. Your character's name becomes `Recorder` wherever the server sends it (your character, the loading screen, the party and team rows, items customized for you, quest texts naming you), your account's name becomes `Recorder` too, and your mercenary heroes, named after your other characters, become `Mercenary 1`, `Mercenary 2`... With either setting on, guild names become `Guild 1`, `Guild 2`... and guild tags `G1`, `G2`... A replay shows these placeholders: the game never compares a name in a recording with your own, and the same name always gets the same placeholder within a recording.
- **Folder** — where recordings go. Empty means the `replays` folder inside the toolbox's settings folder; **Open** shows it in Explorer.
- **Size cap per recording (MB)** — a recording stops growing at this size and is marked as capped.
- **List recordings in the Observe window** — off by default. See [Recordings in the Observe window](#recordings-in-the-observe-window).
- **Play recordings from the Observe window** — off by default; needs the list. See [Playing a recording](#playing-a-recording).

The panel shows the recording in progress (messages, size, layout errors) or the last one saved. A recording's header is on disk from its first moment; a recording ends with its header complete on a map change, at the character screen, after a minute with no message, when the module is turned off and when the game closes. A recording with no message is removed, and an empty file left by a game that stopped before it could write one is removed when the Observe window lists the folder. A solo hour in an explorable area is about 120,000 to 150,000 messages, 2 to 3 MB.

## Recordings in the Observe window

With **List recordings in the Observe window** on, your recordings appear in the game's own Observe window (**B** in a town or outpost), next to the matches the server lists, under the category **Custom Event (0)**. Each row is named `Replay <date> <time> (<length>)`; its card shows the map and when the recording began ("Started N minutes ago").

- The rows are built from each file's header alone, when the server's list arrives. A file is left out if its header is not a recording's, if it was recorded on another client build or with another message table, if it is unfinished or empty, or if it is an outpost's (see [Playing a recording](#playing-a-recording)); the toolbox's log names each file left out and why. The newest 100 recordings are listed.
- Choosing one of these rows and pressing **Observe** plays it when **Play recordings from the Observe window** is on (below); otherwise the toolbox answers in chat with the recording's file, map and length. **Nothing is sent to the server** for these rows: the toolbox catches the choice before the game sends it, and every other row is observed as usual.
- The rows use keys of their own (`0x52500000` to `0x5250FFFF`), never one the server's list already holds. Turning the setting off, or unloading the toolbox, clears them from the window's list first, so the game cannot send one of them afterwards; the server's own rows come back at the window's next refresh (every 15 seconds).

`replay_check --rows <folder>` prints the rows the toolbox would list for a folder, with the same code, and checks each one against the client's own layout for the Observe window's rows as the newest recording carries it.

## Playing a recording

With **Play recordings from the Observe window** on, **Observe** on one of your rows plays that recording in the game's observer mode: the loading screen, then the map as it was, seen from the observer's camera (Auto Camera, Hide UI, the Observers chat channel), with every agent, effect and move the server sent. Leave it with the game's own stop observing (**B**, then **Yes**): the game asks to go back to the map you were on before observing, as after any observed match, and you are back in your outpost.

While a recording plays, the **Replay** window shows (it is listed with the toolbox's windows and draws only during a replay):
- the recording's time and length on a progress bar, **Pause** and **Resume**, and a speed: x1, x2, x4 or x8. Pause and the speeds act on the game's clock of agents (the one that moves them between the server's messages) as well as on the recording, so agents stop where they are and move at the chosen speed without jumping. Animations keep the game's own pace;
- **Stop**, which leaves as stop observing does, and **Restart**, which leaves the same way and, once you are back in the outpost and its connection is settled (a few seconds), plays the same recording again from its start;
- at the recording's end, the replay stays on its last moment, paused, until you stop or restart;
- **Follow the agent I select** (on by default): select a hero, a henchman or anyone else, by a click, the party window or a key, and the view follows it, as an observer's view follows the player it picks. **Back to the recorder's character** returns to the recorder;
- the skills of the selected agent, or of the followed one: the recording holds the skill bars of the recorder and its heroes only, as the server sends no others.

Turning the setting off, disabling the module or unloading the toolbox also stops a replay as **Stop** does; the toolbox waits for the game to leave the replay before it unloads.

The world map opens during a replay only when the map you left for it is on the replay's continent: the game draws the world map of the map you left over the explored areas the recording brings, and it asserts that the two are the same continent. Otherwise it stays closed, and a chat line says why. The mission map stays closed during a replay, with a chat line: in observer mode the game draws it from a PvP map's image, which a PvE map does not have, so it would be black.

Closing the game during a replay first closes the replay's connection, as **Stop** would, so that the game's own shutdown finds only its real connections.

How it works, and what reaches the server:
- The toolbox gives the game a transfer to a game server of its own making (the loopback address and a closed port), then takes over the connection the game opens for it: the game gets a connection with no network socket, the kind its own playback code runs on, and everything the game sends on it goes nowhere. The game server you were on gets the game's usual goodbye before a transfer.
- The recording is fed into that connection as the server sent it and as the game accepted it when it was recorded, from the first message of the map's connection (380), in its order: everything before the map's load (406) when the connection is ready, then up to the agents' start (31) when the game acknowledges the instance, then the rest when the game has loaded the map, at the recorded times counted from 31's. Only two things change, and each playback's log line lists them: the few messages the recording holds from the previous map's connection, before 380, are left out, and the instance information (410) gets its observer byte, which puts the game in observer mode and keeps the map you came from to go back to. The recorder's own messages (inventory, attributes, heroes, skill bars) stay: the game's observer mode reads its observer flag only in the interface (it builds the observer's panels instead of the player's) and to word one mission message in chat.
- Outposts are not played, nor listed: the observer's party window asserts that the map it observes is a game map.
- In a real observed match, the camera follows the agent the observer's server names (a message the game handles as for any observer); what you select is sent to that server, which answers with it. A recording has no such server, so the toolbox gives the game that message itself for the agent you select. If the game's handler for that message is not the one the toolbox knows, following is off and the panel's status says which check failed. Auto Camera is also sent to that server; in the game itself it centres the camera on the agents around the followed one, which is all it does in a replay.
- Each step of a playback (the transfer, the connection ready, each part of the start fed, the end) is written to the toolbox's log file as it happens.
- Nothing of the replay is sent to ArenaNet's servers. Your account's login connection stays as it is; stop observing is the only message it gets, the same one as after any observed match. The clock the toolbox pauses and speeds up is the agents' alone: the timers of the connections to ArenaNet are never touched.
- The transfer to the replay is given only when the game is not joining a map of its own: a transfer given during a join is kept by the game for that join's end, so the toolbox waits for it to end first.
- Each game function the toolbox uses is found by its code when the setting is turned on. If one is missing (a game update), nothing is hooked, playback stays off and the panel says which one; the rows are still listed. With the setting off, nothing of playback is hooked.

## Reading a recording

`replay_check`, built with `python scripts/build.py --target replay_check`, prints a recording's header and the count, bytes and kind (see [Message kinds](#message-kinds)) of each message id:

```
replay_check <recording.gwrec>
replay_check --state <recording.gwrec> <ms>
replay_check --join <recording.gwrec> <ms> <out.gwrec>
replay_check --check-join <recording.gwrec>
replay_check --keyframes <recording.gwrec> <interval ms> <sample ms>
replay_check --wire <recording.gwrec>
replay_check --feed <recording.gwrec> <ms>
replay_check --order <recording.gwrec>
replay_check --mine <recording.gwrec>...
replay_check --strip <recording.gwrec> <out.gwrec>
replay_check --no-names <stripped.gwrec> <original.gwrec> [name...]
replay_check --rows <folder> [client build]
replay_check --self-test <folder>
```

- `--state` prints the instance's state after the records up to that time: its clock and its agents, with what each holds as message and agent ids only (no names, texts or values), and a digest of the whole state.
- `--join` writes a recording that starts at that time: the join that recreates the state (below), then the rest of the stream.
- `--check-join` checks a recording against what the client asserts when it enters an instance (below).
- `--keyframes` proves a recording's joins. For each keyframe, the state rebuilt from its join and the records after it must equal the whole stream's state at every sample time. Each keyframe's join must pass `--check-join`. A seek between two keyframes must give the stream's state. Every record must decode against the file's table and encode back to its bytes.
- `--wire` checks a recording's playback on the wire: the plan the toolbox feeds is encrypted post by post with an RC4 state, decrypted, cut back into messages by the file's table and encoded again, and must come back byte for byte.
- `--feed` prints that plan up to a time: its changes from the recording, then each post in order with when it is sent (after the connection is ready, after the game acknowledges the instance, after the map is loaded, or its time in the recording), its message count, size and first message ids (no names). It proves the plan is the recording byte for byte but for the changes it lists: each message fed is the next record not listed as left out, in the stage and at the time the recording puts it, with the recorded bytes, or for a listed 410 the recorded bytes with the observer byte alone set; only records before the connection's first 380 or from a second map load in the file may be left out, and every other record is fed. It also checks the stages' order, that every post cuts into its messages, what the game asserts for characters (as `--check-join`) and [the order of real loads](#the-order-of-real-loads).
- `--order` checks the order of real loads on the plan and on the joins (see [Restoring any moment](#restoring-any-moment)) at 10 s, 30 s, 60 s and the end of the recording with the stream after each, and counts each join's failures by message and kind of id. It fails only when the plan fails.
- `--mine` reads recordings and prints, for each kind of id, which message fields first brought an id of that kind in and which only ever came after one, and whether the toolbox's rules (`ReplayState::BringsIdsIn`) are those.
- `--strip` writes a copy of a recording with both name settings applied, by the module's own code: other players' names, the recorder's (from the instance's player name, or the recorder's character), the account's, mercenaries', guilds' names and tags replaced. The copy plays like any recording: `--feed`, `--wire` and `--order` apply to it.
- `--no-names` proves a stripped recording holds none of the original's names: the recorder's, the account's, the mercenaries', the guilds' names and tags, and any name given on the command line. It looks in every text of every record and in the records' bytes, and prints counts and message ids only, never a name. A name that is itself part of a placeholder (a recording already stripped of it holds `Player 1` where the name was) is looked for outside the placeholders.
- `--rows` lists the rows the Observe window would get from a folder (key, map, type, category, age, length; no names) and the files left out with their reasons. Each row must pack and read back by the 414 layout of the newest recording (or the newest of the given client build), its type must be one the window has a category for, and its key must be in the toolbox's range and unique.
- `--self-test` writes synthetic recordings into the folder with the module's own writer, reads them back and checks that every record, the header and the message table come back exactly as written. It also writes a synthetic instance (players, NPCs, a gadget, an item on the ground, moves, effects, damage, deaths and returns, the recorder's character messages and a hero's) and runs the `--keyframes` proof on it, with keyframes every 10 s and every second, then the `--feed` and `--wire` proofs (the RC4 step checked against the textbook cipher). A join plan with the recorder's character messages taken out must fail `--feed`, a plan with its guild message (280) moved first must fail the order of real loads, a plan with one byte changed or one record dropped that it does not list must fail the byte-for-byte proof, and a recording with no 55 for the recorder's character must give a join without its 34, 89 and 32. It also checks the name settings: each kind of name gets its placeholder, the same name keeps it, a name inside a game text is replaced, and each setting alone leaves the other's names as they were.

## Restoring any moment

A replay that starts in the middle of a recording, or seeks, cannot feed the client the stream from that point: the later messages assume every agent, effect and quest made before. `replay_check` keeps the instance's state as the records come (`GWToolboxdll/Utils/ReplayState.*`, which does not depend on the game) and turns it back into the messages an instance's entry sends.

**What the state holds**:
- The entry: 380, 390, 381, 410 (its observer byte cleared), the manifest's 409, 407 and 408, 428, 406, 186 and 398, as the recording had them.
- The agents' clock: 31's time, then each 30's milliseconds added.
- Every agent alive (32 until 33) and its creation, with its position kept current:
  - Its walk (41 or 42) advances at each 30, in a straight line to its point, at its speed (39, else 32's) times its move speed (43, else 32's), until it arrives; 44 moves it, 40 stops it.
  - Its last 36, 37, 38, 39, 43, 46 (until 45), 47, 53, 72, 109, 154, 155, 156, 166, 170 (until 62), 174 and 277; its status (240, 241); its equipment (110, 111).
  - Its health and energy: set by 162 (kinds 34 and 33), changed by 163 (kinds 16, 17, 18, 55) and 162 (kind 62), regenerated at each 30 by 162 (kinds 44 and 43).
  - Its effects (66, until 68 or the end of their duration), upkeeps (63 and 65, until 64), auras (159 kinds 6 and 7) and lasting notices (159 kinds 11, 12, 30, 36, 41, 42, 66).
- Messages about an agent not yet created (154, 155, 159, 166, 170, 240, 241), kept for that agent's creation and dropped at the next 30 when it does not come.
- The players' rows (89, until 90) with their agent, even one out of the world, and their flags (60); the reporter (34).
- The instance: 242, 430, the quests (73, 76, 77, 80, 81, 83, 84, until 82), NPC and gadget definitions (86, 87, 263), props (270, 273), 141's table, guilds (280, 284, 288, 289, 302), the party (435, 446, 447, 451, 460, 467, 468, 474), 107, 112, 176, 177, 366 and 404.
- Item details (353, 354, 350, 346, 314, 309), sent again only for the items ever shown (worn, 110 and 111; held, 109; on the ground; in a weapon set, 327) and for the items never put in the recorder's inventory (318).

**The join** at a time is, in order:
1. 380, 390, 381, and 410 with its observer byte set; 409, 407 and 408; 428; the quests; 406; 430; 242; then the recorder's character, as the entry sends it: its attribute state (55, with the later 56 and 57 in it), professions (183, 182), skill bar (218, marked to be made), attributes (58) and the changes since (59).
2. 31 with the clock; the details of those items.
3. The recorder's own row (89) and agent, then every agent that is not a player's. Each agent comes as the entry sends it: its definitions, its rows, 32, its items, its equipment and state, its health and energy, its effects with their remaining time.
4. 34 for the recorder's character, which the viewer controls.
5. The other players' rows and agents; the walks under way and the upkeeps.
6. The players' flags (of the players still in the instance), the guilds (288 and 289 before 280, as real loads send them), the props (273 before 270), the rest of the instance and the party; 186 and 398; 366 and 404.

Private messages are not in a join, but for the recorder's character above. The game keeps an attribute state for each character, made only by 55, and asserts it exists when 34 makes that character the one it controls (its skill list reads every attribute of the controlled character and of every active hero) and when 56 to 59 or 183 come. Without it the viewer's game stops on the join. If a recording holds no 55 for the recorder's character, the join leaves out its 34, 89 and 32: the viewer then has no character of its own. The heroes' private messages stay out: the game reads their attribute states only for heroes made active (114, which needs the hero's 115), and neither is sent. After a join, the stream carries the recorder's character messages (55 to 59, 182, 183, 218) and no other private message.

**Keyframes**: the state is kept every N seconds of the recording (10 by default), in memory, at the first 30 after each multiple; the file format does not change. A seek to a time is the nearest keyframe's join, then the records from that keyframe to the time.

**What `--check-join` checks**, as the client asserts or needs:
- 410 before 408, and 409 before 407.
- No agent message (32 to 47) before 31.
- 242 before 34, and the reporter's agent created as a player first (89, then 32) with 242's team token.
- What the game asserts for characters: one 55 an agent; 56 to 59 and 183 after it; a hero's data (115, or 116 for a mercenary) before its 114; at 34, an attribute state for the agent and for every active hero.
- No message naming an agent that is not alive, except the rows the entry sends just before an agent's own 32, and the recorder's character messages before 31.
- Every record decodes against the file's table and encodes back to its bytes.

After the join, the stream's own character-client messages about agents not created are counted rather than failed, because the game server sends them. So are player rows naming an agent out of the world: the server sends those too, and the client keeps them.

### The order of real loads

A message that names an id (an agent, item, bag, inventory, guild, party, player, quest, hero, NPC or prop) must come after a message that brings that id in, as in every load the game server sent. Which fields bring ids in was read from real recordings (`--mine`): for instance a guild comes with 288 or 289, which 280 always follows; an item with 353, 354 or 350; an inventory with 324; a bag with 319; a party with 467; a quest with 80 or 73; a hero with 115 or 116; an NPC with 86; a prop with 273; an agent with its 32 or the rows the server sends before it. Skill ids are the game's own data and are not checked. A plan that breaks one of these makes the game look up something it was never given.

### Message kinds

Every server message id is one of these (`replay_check <recording>` prints each id's kind):
- **State**, what the join restores (above): 30-34, 36-47, 53, 60, 62-66, 68, 72, 73, 76, 77, 80-84, 86, 87, 89, 90, 107, 109-112, 141, 154-156, 159, 162, 163, 166, 170, 174, 176, 177, 186, 240-242, 263, 270, 273, 277, 280, 284, 288, 289, 302, 309, 314, 346, 350, 353, 354, 366, 380, 381, 390, 398, 404, 406-410, 428, 430, 435, 446, 447, 451, 460, 467, 468, 474. Some kinds within these are one-off and dropped: 159's other kinds (attacks, casts, animations), 162's kinds 52 and 63, 163's kinds 52 and 61.
- **Transient**, safe to drop at a join: 12 and 13 (ping), 35, 52, 61, 69 and 71 (the client only posts them to its interface), 70 (a screen shake), 93, 94, 96 and 97 (chat), 160, 161, 164, 165 and 226-228 (attacks, casts, projectiles, speech), 345 (a pick-up).
- **Private**, the recorder's own and not in a join but for the recorder's character (above): 15, 48-51, 54-59, 75, 78, 92 (acted on only for the controlled character), 101, 114 (a hero made active), 115, 116, 124-126, 128, 129, 131, 132, 138-140, 181-183, 195-197, 202-204, 218, 219, 221, 224, 229, 230, 233-239, 243-246, 313, 318-321, 324, 327, 328, 331, 333, 335, 337 and 479-481. These are the inventory, gold, skill bars, attributes, titles, account, heroes' builds, explored map, dialogs, windows and party search.
- **Unknown**, dropped from a join: 74, 153, 167, 207 and 360, seen in recordings but not understood. Each handler calls one function that was not read:
  - 74 and 153 call 0x0059b2e0, then post a frame message.
  - 167 calls one of two functions, by the agent's kind. It mostly names agents that are not created.
  - 207 calls 0x00820040.
  - 360 calls a function of the agent view, by the agent's model kind.

  Any id not listed is unknown too; none was seen in the recordings at hand.

## File format

Each recording is a `.gwrec` file named after its start time and map, e.g. `2026-11-23_14-05-12_map148.gwrec`. All numbers are little-endian. Version 1 is not compressed and has no index.

**Header** (96 bytes, rewritten when the recording ends):

| Offset | Size | Field |
|---|---|---|
| 0 | 8 | magic `GWTBREC\0` |
| 8 | 2 | format version (1) |
| 10 | 2 | header size (96) |
| 12 | 4 | client build (the game's version) |
| 16 | 8 | digest of the message table (FNV-1a 64 over its bytes) |
| 24 | 8 | start time, Unix milliseconds, UTC |
| 32 | 4 | duration, milliseconds |
| 36 | 4 | map id |
| 40 | 4 | the map's region type |
| 44 | 4 | 1 for an explorable area, 0 for an outpost |
| 48 | 4 | district |
| 52 | 4 | server region |
| 56 | 4 | language |
| 60 | 4 | record count |
| 64 | 4 | layout errors: messages saved as their id alone |
| 68 | 4 | flags: 1 names stripped, 2 chat dropped, 4 complete, 8 size cap reached, 16 own names stripped |
| 72 | 24 | toolbox version, NUL-terminated |

A file without the *complete* flag was cut short (the game closed or crashed): its header's counts and duration are zero, and its records are still readable up to the last whole one.

**Message table**, right after the header: a `u32` count of server message ids, then for each id a `u32` count of field descriptors and the descriptors (`u32` each), as the client held them when recording. Its first descriptor is the message id's own. This makes every file readable without the client that recorded it.

**Records**, until the end of the file: a `u32` time in milliseconds since the start, a `u16` length, then the message as the server sent it on the wire: a `u16` message id followed by its fields, packed with no padding. Ids, floats and 4-byte numbers take 4 bytes; numbers 1, 2 or 4 bytes as their descriptor says; a blob its bytes; a text a `u16` length then that many UTF-16 units; an array a `u16` count then its items; a repeated group a `u8` count then the remaining fields once per repetition. The server's transfer to the next map (message 422, which carries its address and keys) is never recorded.
