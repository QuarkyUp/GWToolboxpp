All settings for this feature live under <ToolboxPath steps={["Settings", "Replay Recorder"]} />. The module is off by default: turn it on under <ToolboxPath steps={["Settings", "Toolbox Modules"]} />.

The Replay Recorder saves every message the game server sends while you are in PvE maps, from the moment you press **Record** until **Stop** or logging off, in one file across map changes, with the time each one arrived. It only reads what the client already received and changes nothing in the game. PvP maps and observed matches are never recorded: a transfer to a PvP map ends the recording. A recording can be played back in the game's own observer mode, from the Observe window (see [Playing a recording](#playing-a-recording)).

A recording keeps, besides the server's messages, **keyframes**: the moment as the game holds it, read from the client's memory and written as the messages a server sends a player entering the map. One is taken when the recording starts, one after each map's load, and one every 30 seconds. A replay starts from a keyframe: the first one of the recording's first explorable map.

Each map of a recording is a **chapter**: its map, whether it is an explorable area or an outpost, and when it began.

## Settings

- **Record** and **Stop recording** — start now, in a loaded PvE map (a recording asked for during a loading screen starts once the map is loaded), and end. The panel shows the recording in progress (chapters, keyframes, messages, size) or the last one saved.
- **Start recording when entering the game** — records from the first map after you log in, until you log off. **Stop recording** ends it until the next login.
- **Keep other players' names and chat out of recordings** — on by default. Other players' names become `Player 1`, `Player 2`... (the same player keeps the same label within a recording) and player chat and player speech bubbles are left out. Every name the server sends as plain text is relabelled this way; NPC chat and system messages are kept.
- **Keep my own names out of recordings** — on by default. Your character's name becomes `Recorder` wherever the server sends it (your character, the loading screen, the party and team rows, items customized for you, quest texts naming you), your account's name becomes `Recorder` too, and your mercenary heroes, named after your other characters, become `Mercenary 1`, `Mercenary 2`... With either setting on, guild names become `Guild 1`, `Guild 2`... and guild tags `G1`, `G2`... A replay shows these placeholders: the game never compares a name in a recording with your own, and the same name always gets the same placeholder within a recording. Keyframes read from memory go through the same settings.
- **Folder** — where recordings go. Empty means the `replays` folder inside the toolbox's settings folder; **Open** shows it in Explorer.
- **Size cap per recording (MB)** — a recording stops growing at this size and is marked as capped.
- **List recordings in the Observe window** — off by default. See [Recordings in the Observe window](#recordings-in-the-observe-window).
- **Play recordings from the Observe window** — off by default; needs the list. See [Playing a recording](#playing-a-recording).

**A recording never holds your inventory**, whatever the settings: no bag, bag content, storage, gold, currency, trade or merchant window. It keeps only the items someone wears or holds (weapons, armour, costumes) and the items lying on the ground; an item you equip during the recording is written just before the message that equips it.

A recording's header is on disk from its first moment; it ends with its header complete at **Stop**, when you log off, after a minute with no message, before a PvP map, when the module is turned off and when the game closes. A recording with no message is removed, and an empty file left by a game that stopped before it could write one is removed when the Observe window lists the folder. Nothing is hooked while you are not recording and the login setting is off.

## Recordings in the Observe window

With **List recordings in the Observe window** on, your recordings appear in the game's own Observe window (**B** in a town or outpost), next to the matches the server lists, under the category **Custom Event (0)**. Each recording gets one row, `Replay <date> <time>, <N> maps, <length>`, which plays from the first keyframe of its first explorable map; a recording of outposts alone ends with `, outposts` and is listed but not played yet. A row's card shows that map and when the recording began ("Started N minutes ago").

- The rows are built from each file's header and index (its chapters and keyframes), when the server's list arrives. A file is left out if its header is not a recording's, if it was recorded on another client build or with another message table, or if it is unfinished or empty; the toolbox's log names each file left out and why. The newest 100 recordings are listed.
- Choosing one of these rows and pressing **Observe** plays it when **Play recordings from the Observe window** is on (below); otherwise the toolbox answers in chat with the recording's file, map and length. A row of outposts alone is answered in chat: the observer's party window asserts that the map it observes is a game map, so outposts are not played yet. **Nothing is sent to the server** for these rows: the toolbox catches the choice before the game sends it, and every other row is observed as usual.
- The rows use keys of their own (`0x52500000` to `0x5250FFFF`), never one the server's list already holds. Turning the setting off, or unloading the toolbox, clears them from the window's list first, so the game cannot send one of them afterwards; the server's own rows come back at the window's next refresh (every 15 seconds).

`replay_check --rows <folder>` prints the rows the toolbox would list for a folder, with the same code, and checks each one against the client's own layout for the Observe window's rows as the newest recording carries it.

## Playing a recording

With **Play recordings from the Observe window** on, **Observe** on one of your rows plays that recording from its keyframe in the game's observer mode: the loading screen, then the map as it was, seen from the observer's camera (Auto Camera, Hide UI, the Observers chat channel), with every agent, effect and move the server sent. Leave it with the game's own stop observing (**B**, then **Yes**): the game asks to go back to the map you were on before observing, as after any observed match, and you are back in your outpost.

While a recording plays, the **Replay** window shows (it is listed with the toolbox's windows and draws only during a replay):
- the recording's time and length on a progress bar, **Pause** and **Resume**, and a speed: x1, x2, x4 or x8. Pause and the speeds act on the game's clock of agents (the one that moves them between the server's messages) as well as on the recording, so agents stop where they are and move at the chosen speed without jumping. Animations keep the game's own pace;
- **Stop**, which leaves as stop observing does, and **Restart**, which leaves the same way and, once you are back in the outpost and its connection is settled (a few seconds), plays the same recording again from the same keyframe;
- at the end of the keyframe's map (the next map is not played yet), the replay stays on its last moment, paused, until you stop or restart;
- **Follow the agent I select** (on by default): select a hero, a henchman or anyone else, by a click, the party window or a key, and the view follows it, as an observer's view follows the player it picks. **Back to the recorder's character** returns to the recorder;
- the skills of the selected agent, or of the followed one: the recording holds the skill bars of the recorder and its heroes only, as the server sends no others.

Turning the setting off, disabling the module or unloading the toolbox also stops a replay as **Stop** does; the toolbox waits for the game to leave the replay before it unloads.

The world map stays closed during a replay, with a chat line: the game would draw the world map of the map you left over explored areas, which a keyframe does not hold, and it asserts that the two match. The mission map stays closed during a replay, with a chat line: in observer mode the game draws it from a PvP map's image, which a PvE map does not have, so it would be black.

Closing the game during a replay first closes the replay's connection, as **Stop** would, so that the game's own shutdown finds only its real connections.

How it works, and what reaches the server:
- The toolbox gives the game a transfer to a game server of its own making (the loopback address and a closed port), then takes over the connection the game opens for it: the game gets a connection with no network socket, the kind its own playback code runs on, and everything the game sends on it goes nowhere. The game server you were on gets the game's usual goodbye before a transfer.
- The keyframe's messages are fed into that connection in a server's order: everything before the map's load (406) when the connection is ready, then up to the agents' start (31) when the game acknowledges the instance, then the rest when the game has loaded the map. Its instance information (410) gets its observer byte, which puts the game in observer mode and keeps the map you came from to go back to; each playback's log line lists that change. The map's messages after the keyframe follow at their recorded times. The recorder's own messages (attributes, heroes, skill bars) stay: the game's observer mode reads its observer flag only in the interface (it builds the observer's panels instead of the player's) and to word one mission message in chat. A message naming something the keyframe does not hold (an agent, item or inventory that neither the keyframe nor an earlier message brought in) is left out, and the log line counts them.
- In a real observed match, the camera follows the agent the observer's server names (a message the game handles as for any observer); what you select is sent to that server, which answers with it. A recording has no such server, so the toolbox gives the game that message itself for the agent you select. If the game's handler for that message is not the one the toolbox knows, following is off and the panel's status says which check failed. Auto Camera is also sent to that server; in the game itself it centres the camera on the agents around the followed one, which is all it does in a replay.
- Each step of a playback (the transfer, the connection ready, each part of the start fed, the end) is written to the toolbox's log file as it happens.
- Nothing of the replay is sent to ArenaNet's servers. Your account's login connection stays as it is; stop observing is the only message it gets, the same one as after any observed match. The clock the toolbox pauses and speeds up is the agents' alone: the timers of the connections to ArenaNet are never touched.
- The transfer to the replay is given only when the game is not joining a map of its own: a transfer given during a join is kept by the game for that join's end, so the toolbox waits for it to end first.
- Each game function the toolbox uses is found by its code when the setting is turned on. If one is missing (a game update), nothing is hooked, playback stays off and the panel says which one; the rows are still listed. With the setting off, nothing of playback is hooked.

## Reading a recording

`replay_check`, built with `python scripts/build.py --target replay_check`, checks recordings offline, with the module's own code:

```
replay_check --compare <recording.gwrec>
replay_check --feed <recording.gwrec> <ms>
replay_check --wire <recording.gwrec>
replay_check --order <recording.gwrec>
replay_check --rows <folder> [client build]
replay_check --self-test <folder>
```

- `--compare` prints a recording's chapters and keyframes (their kind, time, messages and size), then, for each chapter with a load, compares that load with the join the toolbox's model of the game's state builds from it: message by message, by what each one is about (an agent and its kind of row, an item, a quest...), counting the equal ones, the repeats (the server sends some rows twice; the model keeps the latest), and the missing, extra or differing ones by field, each with the reason the toolbox lists for it. For every keyframe after a map's load (the one after the load and those every 30 seconds), it compares the keyframe, read from the game's memory, with the model of the recording up to it, each difference with its reason, and counts the keyframe's messages its file's table does not read. It also counts what the inventory rule leaves out (a recording must hold none) and checks the names: with the names settings on, every plain text and every name inside a game text, in the stream and in every keyframe, must be a placeholder. It prints message ids, field numbers and counts, never a name or a text.
- `--feed` prints the plan of each start of a recording (each keyframe, and the keyframe the model builds after each map's load) up to a time: its changes from the recording, then each post in order with when it is sent (after the connection is ready, after the game acknowledges the instance, after the map is loaded, or its time in the recording), its message count, size and first message ids. A keyframe the toolbox refuses (one whose messages its table does not read) is reported and not played. It checks for every plan the stages' order, that every post cuts into its messages, what the game asserts for characters and [the order of real loads](#the-order-of-real-loads).
- `--wire` checks each plan on the wire: encrypted post by post with an RC4 state, decrypted, cut back into messages by the file's table and encoded again, it must come back byte for byte.
- `--order` checks the order of real loads and what the game asserts for characters on every start, and on keyframes the model builds at 10 s, 30 s, 60 s and the end of each explorable chapter (with their size and the time the model took).
- `--rows` lists the rows the Observe window would get from a folder (key, map, type, category, age, length; no names) and the files left out with their reasons. Each row must pack and read back by the 414 layout of the newest recording (or the newest of the given client build), its type must be one the window has a category for, and its key must be in the toolbox's range and unique.
- `--self-test` writes synthetic recordings with the module's own writer and checks them: a recording of two chapters and two keyframes reads back exactly as written, and every start of it plays; a synthetic map (players, NPCs, an item on the ground, moves, effects, deaths, the recorder's character and a hero) gives a join that holds what the game needs, in the order of real loads and with no bag content; mutated plans fail (the guild message moved first, the recorder's attribute state taken out); a name that is not a placeholder in a keyframe is found; and the name settings give each kind of name its placeholder.

## The game's state, and keyframes

The toolbox keeps a model of a map's state (`GWToolboxdll/Utils/ReplayState.*`, which does not depend on the game) and turns it back into the messages a server sends a player entering the map: the instance's head and information, the inventories' creation, quests, factions and account, the manifest, the map; each character's attribute state, professions, skill bar and attributes, the heroes' data and their activation; the agents' clock (31); every agent with its definitions, rows, creation, equipment and its items, state, health and effects; the players, the controlled character (34), the upkeeps and walks; guilds, props and the party. `replay_check --compare` proves this model on every recording's real load. When recording, a keyframe fills the same model from the game's memory (through GWCA) instead of from the server's messages, and writes the messages it builds.

A keyframe read from memory leaves out what the toolbox cannot read from the game: the explored areas, gadgets and props, guilds, titles, the attribute points, morale, capes, scales, moves in progress, and a few values whose use is unknown. What agents wear comes from the game's own record of it, the map's file from the map's load or the toolbox's map data. The log line of each keyframe gives its messages, size and the time it took, and counts any message the client's own layout refused.

### The order of real loads

A message that names an id (an agent, item, bag, inventory, guild, party, player, quest, hero, NPC or prop) must come after a message that brings that id in, as in every load the game server sent: for instance a guild comes with 288 or 289, which 280 always follows; an item with 353, 354 or 350; an inventory with 324; a party with 467; a quest with 80 or 73; a hero with 115 or 116; an NPC with 86; a prop with 273; an agent with its 32 or the rows the server sends before it. Skill ids are the game's own data and are not checked. A plan that breaks one of these makes the game look up something it was never given.

## File format

Each recording is a `.gwrec` file named after its start time and first map, e.g. `2026-11-24_14-05-12_map148.gwrec`. All numbers are little-endian. It is not compressed. Only version 2 is read, and a file's records begin with a chapter.

**Header** (96 bytes, rewritten when the recording ends):

| Offset | Size | Field |
|---|---|---|
| 0 | 8 | magic `GWTBREC\0` |
| 8 | 2 | format version (2) |
| 10 | 2 | header size (96) |
| 12 | 4 | client build (the game's version) |
| 16 | 8 | digest of the message table (FNV-1a 64 over its bytes) |
| 24 | 8 | start time, Unix milliseconds, UTC |
| 32 | 4 | duration, milliseconds |
| 36 | 4 | the first chapter's map id |
| 40 | 4 | the map's region type |
| 44 | 4 | 1 for an explorable area, 0 for an outpost |
| 48 | 4 | district |
| 52 | 4 | server region |
| 56 | 4 | language |
| 60 | 4 | record count (the server's messages, not the chapters' and keyframes' entries) |
| 64 | 4 | layout errors: messages saved as their id alone |
| 68 | 4 | flags: 1 names stripped, 2 chat dropped, 4 complete, 8 size cap reached, 16 own names stripped |
| 72 | 24 | toolbox version, NUL-terminated |

A file without the *complete* flag was cut short (the game closed or crashed): its header's counts and duration are zero, and its records are still readable up to the last whole one.

**Message table**, right after the header: a `u32` count of server message ids, then for each id a `u32` count of field descriptors and the descriptors (`u32` each), as the client held them when recording. Its first descriptor is the message id's own. This makes every file readable without the client that recorded it.

**Records**, until the end of the file: a `u32` time in milliseconds since the start, a `u16` length, then the message as the server sent it on the wire: a `u16` message id followed by its fields, packed with no padding. Ids, floats and 4-byte numbers take 4 bytes; numbers 1, 2 or 4 bytes as their descriptor says; a blob its bytes; a text a `u16` length then that many UTF-16 units; an array a `u16` count then its items; a repeated group a `u8` count then the remaining fields once per repetition. The server's transfer to the next map (message 422, which carries its address and keys) is never recorded: it opens the next chapter.

Two entries among the records use ids beyond any message table:
- `0xF001`, a **chapter**: `u32` map id, `u32` 1 for an explorable area or 0 for an outpost, `u32` the map's region type; its time is when the chapter began, and it comes before the chapter's first message.
- `0xF002`, a **keyframe**: `u8` kind (0 the recording's start, 1 after a map's load, 2 periodic), `u32` the number of messages that follow it, which are the keyframe's own (the moment as messages a server sends, at the keyframe's time). The server's messages continue after them.
